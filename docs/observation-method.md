# 让已有 Agent 使用健康硬件数据的方法论

HealthOS 首先服务于已有 Agent 和健康硬件的人。用户无需更换 Agent；把公开入口交给它，即可开始设备识别、诉求澄清和观察方案设计。真实接入、计算和推送由可替换执行组件承担。

**主张：你的设备，你的 Agent，你关心的健康问题。**

## 一条完整的链路

发现 HealthOS → 了解设备开放能力 → 询问个人诉求 → 将问题映射到可用数据与必要背景 → 用户确认观察计划和权限 → 检查数据质量与个人基线 → 形成证据可追溯的报告 → 复盘行动与感受 → 更新经授权的个人记忆。

面向 Agent 的完整协议放在 [observation-method.md](../skills/healthos/references/observation-method.md)，可随 Skill 文件夹一起安装。它包含问题与指标映射、必要访谈、证据边界、反馈方法和缺失数据处理。机器可读[观察计划模板](../skills/healthos/references/observation-plan-v1.json)用于交接提案，当前不是运行时可自动导入的配置或授权文件。

## 第一轮应该做什么

先问：“你用什么型号的手环或健康设备，最想用它了解什么？”已有答案就继续下一项。随后根据实际型号和手机平台核对数据入口，用用户理解的语言解释可以做什么。无需先看演示或填写模型密钥。

例如，用户说“我有手环，最近总觉得累”。Agent 先区分用户关心的是睡眠、白天精力还是运动恢复，询问时间和近期变化，再讨论能够观察哪些记录。不会直接把疲劳归因于 HRV，也不会要求先等待基线收集再寻求需要的医疗帮助。

## 一份观察计划应交付什么

| 项目 | 用户能检查的内容 |
| --- | --- |
| 个人问题 | 想了解什么，报告应帮助做什么决定 |
| 数据来源 | 设备型号、官方入口、开放字段、实际适配器、访问资格与核实日期 |
| 用途与权限 | 使用哪些字段，在哪里处理，保留多久；模型分享和推送分别选择 |
| 观察方法 | 数据频率、历史覆盖、缺失检查、可比较的数据流、计算假设 |
| 证据 | 原始来源支持什么，不支持什么；软件设计与论文结论分开 |
| 报告与复盘 | 报告频率、事实、可能解释、未知、小行动与反馈方式 |
| 可执行下一步 | 当前能做什么，哪些字段、连接器或工具仍缺少 |

## 方法与执行分开

| 层 | 可替换内容 | 当前情况 |
| --- | --- | --- |
| 方法论 | 诉求访谈、观察协议、报告与反馈规则 | 可通过公开文档或 Skill 使用；尚无跨宿主行为验证 |
| 数据 | 官方 OAuth、手机健康平台、导出、受信插件 | 以[当前字段表](start-here.md)为准；厂商开放不等于仓库已集成 |
| 计算 | 数据质量、分流基线、确定性统计 | 有 Python 原型；28/3 天阈值是工程假设 |
| 解释 | 已有 Agent 或可选独立 LLM | 使用已有 Agent 不需要再提供一个模型 key |
| 记忆与执行 | 用户选择的私人存储、调度和投递 | 需要实际工具、运行环境和授权；读链接不会启动后台服务 |

公开研究支持测量纪律、一般健康行动与行为访谈框架。它们没有验证本项目的诊断能力、提醒阈值或健康效果。[证据与计算](report-methodology.md) · [论文到代码的边界](evidence-to-code.md)。
